- **行内标签推荐尖括号语法**（`<color=accent>…</color>`、`<w=500>`、`<w>`），和现有的 `{变量}`、`[if:]`、《》注音都不冲突；Core 只有一份解析器，Lint、Renderer、Authoring、Editor 共用。
- **调查中实际确认了一个现存缺陷：** 中文书名号会被当成注音，书名在画面上缩成小字，在文字记录里直接消失。建议注音只保留一种显式写法 `<ruby=读音>基础字</ruby>`，不带标记的《》按书名号显示；这是公开 DSL 行为的变化，需要 Owner 决定。其余 17 条顺带发现的问题见第 13 节，证据等级各不相同，多数是读代码所得、未实机复现。
- **导出不能直接调用现有的 `surdet pack`：** 它依赖引擎仓库、npm、Vite 和 electron-builder，作者电脑上都没有。推荐“预制运行时 + 内容清单”，由 Editor 用纯 JavaScript 完成导出，同时补上多部游戏之间的存档隔离。
- **需要 Owner 或 GPT 拍板的事** 集中在第 14 节，最重要的是：标签语法、注音写法、文字记录带来的存档变化（D 级）、导出方案。

## 3. 行内文字标签（重点）

**对应：** R12 / P6。总规划 P6 写明“补齐作者可控的文本样式、停顿/显示节奏、Ruby 与 ADV/NVL 排版……富文本需有明确可转义语法和完整文本导出，不引入任意 HTML”。P6a—P6c 交付的是文本映射、多语言播放和已有配音关联（总规划 11.16—11.18，见归档原文），行内样式与节奏还没有实现：DSL 规范里正文只有 `{变量}` 插值和《》注音（`docs/dsl-spec.md:35`、`:76`）。

### 3.1 作者要能写出什么

```gal
凛：你说什么？<w=400>……<color=accent>再说一遍</color>。
沈岳：<size=0.8>其实，</size><w>我一直都知道。
门外传来<shake>咚、咚</shake>的敲门声。
凛：等一下，我还没——<nw>
沈岳：来不及了。
```

对应的效果：强调色、耳语变小、句中停顿、句中等点击、抖动字、被打断的台词直接接下一句。这些是日式 ADV 最常用的文字演出，目前只能拆成多句或放弃。

**现存缺陷（已核实，本轮实际运行 `parseRuby`）：** 中文书名号会被当成注音。`我在读《红楼梦》。` 被解析为基础字“我在读”加注音“红楼梦”：画面上“红楼梦”变成小字压在“我在读”上方，文字记录经 `stripRuby` 后只剩 `我在读。`，书名整个消失。受跟踪剧本还没用过《》，所以目前没人踩到；中文作品里书名号很常见，迟早会遇到。

### 3.3 语法：推荐尖括号标签

| 方案 | 写法 | 主要问题 |
| --- | --- | --- |
| **A 尖括号（推荐）** | `<color=accent>危险</color>`、`<w=500>` | 外观像 HTML，需要说明只是固定的小标签集；颜文字 `>_<` 等靠宽松规则按原文显示 |
| B 花括号（Ren'Py 式） | `{color=#f00}危险{/color}`、`{w}` | 与现有 `{变量}` 插值冲突：`{b}`、`{w}` 和名为 `b`、`w` 的变量无法区分，以后声明一个变量就会悄悄改变显示 |
| C 方括号（KAG/Tyrano 式） | `[color=#f00]危险[/color]`、`[l]` | 与选择肢条件 `[if:...]` 同形；中文正文也会写 `[注]` 之类 |

推荐 A：对现有内容零冲突；和 `{}` 插值、`[if:]` 条件、《》注音三种既有记号互不重叠；开闭成对，嵌套一眼可见；用过 Unity TextMeshPro、Naninovel 的作者也熟悉。它**不是 HTML**：只认登记过的标签名，每个标签最多一个取值，没有属性、脚本、图片或链接，符合 P6 “不引入任意 HTML”。

### 3.4 标签清单（分三批）

### 3.5 解析规则

```text
开标签  <名称> 或 <名称=值>
闭标签  </名称>
单标签  <w>、<w=值>、<nw>
名称    只限登记表里的小写 ASCII 名称
值      1–32 个字符，不含空白、尖括号、中英文冒号
转义    \< 输出 <；\\ 输出 \；其他反斜杠按原样显示
```

- 只有“`<` + 已登记名称 + 合法取值 + `>`”才是标签。`>_<`、`<3`、`a < b`、`<<标题>>` 都按原文显示，作者不用转义。
- 形似标签但名称未登记（例如 `<colr=red>`）：按原文显示，Lint 报 M001 警告并给出最接近的名称。
- 样式、效果、变速标签必须在同一句内闭合并严格嵌套；`<b><i>…</b></i>` 报 M003。
- 标签值里不能用变量（`<color={c}>` 报 M004）。动态样式等第三批的命名样式再考虑。
- 说话人切分（`packages/core/src/dsl/lexer.ts:211`，全项目唯一的切分规则）补一条：首个冒号前的前缀里出现已登记标签时，不算说话人。否则 `<speed=0.5>啊：……` 这样的旁白会被当成说话人“<speed=0.5>啊”。标签取值本身也不允许冒号。
- **解析器只有一份，放在 Core**：纯函数、不依赖 DOM。输出可见单元（字素簇、注音组）、样式区间、控制点（停顿、等待点击、变速、`nw`），以及每一段在源码中的位置（供 Lint 定位、Editor 高亮、术语定位）。Lint、Renderer、Authoring、Editor 都调用它，不各写一套正则。
- **运行时不因为标记出错而中断。** 源剧本中的错误在编译/Lint 阶段报出；运行时遇到坏标记按原文显示。译文中的坏标记在译稿校验时报错，运行时退回原文，沿用当前“缺译、过期或失配时回退原文”的规则（`docs/known-limitations.md` 作品多语言一节）。

新增诊断码族 `M`（行内标记）；现有码族为 L、S、C、J、V、T、TL、W（`docs/dsl-spec.md:244` 起），没有冲突。

| 码 | 级别 | 含义 |
| --- | --- | --- |
| M001 | 警告 | 形似标签但名称未登记，按原文显示 |
| M002 | 错误 | 样式、效果或变速标签没有闭合 |
| M003 | 错误 | 闭标签与最近的开标签不匹配，或没有对应的开标签 |
| M004 | 错误 | 取值缺失、超出范围、格式不对或含插值 |
| M005 | 错误 | 标签用在不支持的位置（说话人；选择肢里的节奏或效果） |
| M006 | 错误 | `<nw>` 不在句末 |
| M007 | 本批不启用 | Owner已批准裸《》就是普通文字；无法区分书名与旧注音意图，不根据猜测警告或改写 |

### 3.6 插值、注音与书名号

1. **转义只发生在解析标记的地方。** 共享的 `interpolate()` 同时用于说话人、正文和选项（`interpreter.ts:278`、`:281`、`:285`）。说话人等不解析标记的消费方不能收到带反斜杠的转义串，所以不改 `interpolate()` 本身，而是让正文和选项另走一条“标记插值”：先在原文或译文模板上解析标记，`{变量}` 作为一个插值单元，填进去的值只当普通文字。顺序固定为：原文 → 取译文（缺译、过期时退回原文）→ 解析标记 → 填入插值。各消费方拿到的结果只有三种：

   | 结果 | 内容 | 谁用 |
   | --- | --- | --- |
   | 原文 | 剧本或译稿里的原样文字，未插值 | 译稿 CSV、配音匹配、Authoring 写操作、Editor 源码与高亮、对象索引与指纹、Lint |
   | 样式串 | 取译文并插值后仍带标记的字符串；填入的变量值已转义，再解析也不会变成标签 | 文本事件 `value`、Renderer 排版、演出快照、文字记录（去掉节奏标签） |
   | 可见文字 | 去掉全部标记后玩家看到的字 | 统计、搜索、术语、文字记录搜索、无障碍名称、自定义界面数据、配音 CSV、审阅呈现、流程图标签 |

   说话人继续走现有的 `interpolate()`，结果不变。源码位置只对原文有意义：Lint 和 Editor 使用解析器给出的原文区间；运行时的译文不回指源码位置。文本事件的 `value` 仍是字符串，存档、回退快照和运行轨迹的字段格式不变（推断：开工前由 GPT 确认没有遗漏的二次解析点）。
2. **注音只保留一种显式写法：`<ruby=读音>基础字</ruby>`。** 不带标记的《》一律按书名号原样显示，3.2 的缺陷随之消失。不再另设竖线简写，避免两套写法并存。
   - 这是公开DSL行为变化，Owner已明确不保留旧写法兼容。旧剧本不自动改写，裸《》始终按字面显示；作者需要注音时显式改用ruby。不能以仓库内没有旧写法宣称外部迁移成本为零。本批不靠猜测读音把普通书名判成错误。
3. `{{`、`}}` 的插值转义保持不变。

### 3.7 播放语义

打字机改为按“可见单元”推进：字素簇用 `Intl.Segmenter` 切分（与 `packages/renderer/src/text-wrap.ts:27` 一致），注音组整组出现，标签本身不占时间。

| 情况 | 规则 |
| --- | --- |
| 正常打字 | 每个单元耗时 = 1000 ÷（玩家速度 × 当前 `<speed>` 倍率）毫秒 |
| `<w=毫秒>` | 打到此处停指定时长；打开菜单期间不计时，沿用现有暂停补偿 |
| `<w>` | 打到此处停住并显示继续提示；点击或回车后继续本句，不进入下一句，也不打断语音 |
| 打字中点击 | 立即显示到下一个 `<w>`，没有就到句末；途中的 `<w=毫秒>` 一并跳过 |
| 快进 | 忽略所有停顿和 `<w>`，和现在一样整句瞬显 |
| 自动播放 | `<w=毫秒>` 照常停；`<w>` 视为一次自动停留（基础停留 + 每字停留 × 上一段可见字数）；句末停留改按**可见字数**计算，顺带修正 `presentation-controller.ts:623` 现在按原始长度计算的问题 |
| `<nw>` | 本句打完立即进入下一句，不等点击、不等语音；快进和自动播放下行为相同 |
| 口型 | 停顿和 `<w>` 期间“说话中”置为否，继续打字时恢复（现有 `setPortraitSpeaking`） |
| 语音 | 不受停顿影响；`<w>` 不停止语音 |
| 切换语言 | 沿用 `replaceText` 的比例进度（`text-buffer.ts:52`），改按可见单元换算；停顿状态清零 |
| 存读档、回退 | 仍从句首重新播放（现有规则），存档格式不变 |
| 已读与“快进遇未读即停” | 仍按整句判断，不变 |

### 3.8 排版与渲染

- 把 `layoutRuby`（`packages/renderer/src/ruby-layout.ts:22`）扩展为通用的富文本排版：输入可见单元和样式区间，按样式测量宽度，继续使用 `wrapCjkMeasure` 的中文避头尾规则；每行行高取该行最大字号；注音组和着重号是不可拆的单元。

## 4. 阅读辅助

**对应：** R12“阅读无障碍”。P5 已要求作品自定义界面做到“键盘焦点、字号/换行、减少动态和长列表必须可用”。

**现状（已核实）：**

- 玩家设置共 11 个字段：文字速度、自动播放两项、五路音量、快进方式、键位方案、作品语言（`packages/renderer/src/settings-store.ts:14-51`）。按设备保存（Electron 为 `userData/settings.json`，浏览器为 localStorage），不进存档。设置页由 8 个步进项加“作品语言”组成，分阅读、声音、显示与输入三页（`examples/shared/player/player.ts:1056-1064`、`packages/renderer/src/layers/menu/menu-layer.ts:553-683`）；作品自定义界面只能绑定其中 8 项（`packages/core/src/project-ui.ts:90`）。同一份字段名单分散在四处：`SettingsStore.load`、`SETTING_STEPS`、`WRITABLE_SETTINGS` 和 Editor `ui-designer.ts:40-43` 的 `SETTING_NAMES`。
- **字号：** 对白、NVL、文字记录都用主题的 `bodySize`（默认 28），行高为其 1.6 倍（`packages/core/src/theme-tokens.ts:105`）。主题只在启动时设置，不过运行中重新 `setTheme` 能重新投影字号（`dialogue-layer.ts:507-545`）。玩家不能调字号。
- **对话框不透明度：** 来自主题 `opacity.panel`，默认 0.94；NVL 底板 0.86、横幅 0.85 写死（`dialogue-layer.ts:276`、`:284-285`）。玩家不能调。
- **减少动态：** 引擎已有 `PresentationPreferences.reducedMotion`，开启后把转场、闪白、擦除、缩放、染色、立绘移动、舞台动作和震动的时长压到 1 毫秒，动态立绘冻结，菜单入场一帧完成（`packages/renderer/src/presentation.ts:2-26`）。但它**没有接到玩家设置**：Player 从不设置它，只有测试在用，也不读取系统的“减少动画”偏好。`@fadein/@fadeout`、时间轴时钟（包括镜头震动 cue）、对话层的选项淡入、横幅和继续提示不受它影响。
- 推断：减少动态下 `@flash` 仍从不透明度 1 开始、1 毫秒后消失，可能仍会画出一帧全白，对光敏玩家不够（待用真实逐帧画面确认）。
- **朗读：** 没有任何 TTS、`speechSynthesis` 或 aria-live；Pixi 的无障碍功能只为按钮生成 DOM 节点（`packages/renderer/src/pixi-stage-host.ts:233`）。

**方案：**

1. **设置字段只登记一次：** 在 Core 新增设置登记表（字段名、类型、范围、默认值、所属页、能否被自定义界面绑定），上面四处名单都从它派生，以后加字段只改一处。这是新增字段的前提，不扩大成设置系统重构。
2. **新增四项设置：**

   | 设置 | 取值 | 作用 |
   | --- | --- | --- |
   | 文字大小 | 80%–140%，默认 100% | 对白、NVL、文字记录、选项按比例缩放（经主题重新投影），系统界面不变；行内 `<size>` 是相对值，跟着一起缩放；放不下时沿用现有滚动合同 |
   | 对话框不透明度 | 0%–100%，默认取作品主题的值 | 覆盖 `opacity.panel`，NVL 底板按同一比例变化 |
   | 减少动态效果 | 开或关；首次启动时跟随系统“减少动画”设置 | 接上现有 `reducedMotion`，并补齐覆盖面：时间轴镜头震动、对话层动效、行内 `<shake>`/`<wave>`；此模式下 `@flash` 直接不闪白 |
   | 朗读未配音的台词 | 开或关，默认关 | 用系统语音读出可见文字（不读标签）；有配音的句子不朗读；推进、快进或打开菜单时停止 |

3. **朗读先验证再承诺：** 开工时先做最小验证，确认 Electron 打包环境下能稳定列出并使用 Windows 系统语音；不行就本轮不交付，也不改用云端语音或其他服务代替。系统语音是玩家电脑上的实时朗读，不生成音频素材，不触及音频生产冻结。
4. **默认外观不变：** 新设置的默认值都等于现在的效果；Starter 和《零点之后》在默认设置下画面不变（总规划 4.2）。
5. **自定义界面：** 新字段进入可绑定名单，作品自己的设置页可以放这些控件；Editor 的 UI 设计器同步列出。

**分工：** GPT 负责设置登记表、四项设置的状态与 Renderer 接线、朗读验证；Claude 负责 Player 设置页里新控件的布局与交互、Editor UI 设计器里的设置项，以及预览工具条上“文字大小”“减少动态”的试看开关。

**验收：** 真实 Player 中逐项修改，画面立即变化，重启后保持；140% 字号下长句不被裁切；开启减少动态后，`@shake`、`@flash`、转场、时间轴镜头震动、行内抖动都不再晃动或闪白（逐帧确认没有全白帧）；自定义界面绑定新设置生效；默认设置下两部示例作品的画面与改动前一致。

## 5. 文字记录随存档

**对应：** R18（保存、读取、回退以及升级后续玩）。能力矩阵现在写着：“文字记录为当前会话级数据，不跨存档持久化。”（`docs/capabilities.json:108`）

**现状（已核实）：**

- 文字记录只在 Renderer 内存里：每条 `{speaker, text, voice?}`，最多 200 条，界面显示最近 120 条（`packages/renderer/src/backlog.ts:8-30`、`dialogue-layer.ts:866`）。只在 `text` 事件追加（包括 NVL），选项和横幅不记录。
- **现存问题（读代码确认，未实机复现）：** 只有鉴赏回想会清空文字记录，并在结束后恢复（`examples/shared/player/player.ts:805-806`、`:848`）；读档、开始新游戏、回退都不清空。读另一个存档后，文字记录里仍是上一段游玩的内容。推断：读档与回退会重新发出当前这句（`interpreter.ts:611`），追加时不去重，这句会重复出现；被回退掉的句子也会留在记录里。
- **存档：** `SAVE_SCHEMA_VERSION = 3`，逐级迁移，迁移后严格校验，未知的顶层字段不拒绝（`packages/core/src/save/save-manager.ts:30-81`、`migrate.ts:17-63`）。演出快照 `presentation.payload` 已经保存了 NVL 当前页（`presentation-controller.ts:1087-1107`）。桌面单个存档上限 10 MiB（`packages/shell/src/save-store.ts`）；浏览器存在 localStorage，应用层没有上限。
- 回退帧是 `{snapshot, presentation, audio}`，最多 50 帧，不含文字记录（`packages/host/src/rollback-runtime.ts`）。

**方案：**

1. **放进演出快照：** 文字记录是阅读历史，不是剧情状态，和 NVL 当前页一样放进 `presentation.payload` 的对白部分，不进 Core 变量或 Profile（总规划 4.2：剧情快照、Profile、设备偏好分开存）。
2. **保存内容：** 每条保存显示名、正文（保留样式标记、去掉节奏标签）、语音键；最多 200 条，与内存容量一致。按 200 条、每条约 120 字估算，每个存档增加约 70 KB（推断，开工时用真实数据测量），远低于桌面 10 MiB 上限；浏览器版需要实测多个存档位时的 localStorage 配额。
3. **同一根因一起修：** 文字记录的生命周期要跟着剧情状态走——读档时换成存档里的记录；开始新游戏时清空；读档或回退重放当前句时不重复追加；读档或回退失败时，当前的记录保持不变。
4. **回退恢复的是内容，不是条数。** 回退帧已经带着演出快照（`{snapshot, presentation, audio}`），文字记录随演出快照一起进入回退帧，回退时恢复当时完整的有界记录。只记条数再截断是错的：记录满了会淘汰最旧的条目，例如容量为 2 时检查点是 [A, B]，追加 C 后变成 [B, C]，条数仍是 2，按条数截断回不到 [A, B]（GPT 已用现有 Backlog 实际验证）。条目内容不可变，回退帧之间可以共享同一批条目对象，只复制引用数组（推断：50 帧 × 200 条引用的内存开销很小，开工时测量）。
5. **语言与语音：** 条目保留写入时的语言和语音键，切换语言不重译旧条目（沿用 `docs/known-limitations.md` 的现有说明）；读档后的历史仍可重播语音，语音文件缺失时静默。
6. **存档范围：** Owner已允许文字记录入档。后续该批实现中，旧存档缺少该字段时记录为空；字段存在但格式不对时按坏档处理，走现有备份恢复。这是有界字段语义，不建立双格式读写或通用迁移层，也不因本条擅自破坏旧档。本次行内文字第一批没有改存档结构。
7. 同步更新 `capabilities.json` 与 `known-limitations.md` 的相关原文。

**分工：** GPT 负责 Renderer 快照、Host 回退、Player 新游戏与读档接线、存档校验；Claude 只在 Editor 预览里确认试玩存读档后文字记录的显示。

**验收：** 存档 → 关闭重启 → 读档，文字记录按顺序显示存档点之前的内容，没有重复；读另一个存档时显示那个存档的记录；新游戏为空；回退后被撤销的句子消失；记录满 200 条、开始淘汰旧条目之后连续回退多步，每一步的记录都与当时完全一致；读档或回退失败时当前记录不变；读档后历史语音可以重播；没有该字段的旧存档正常读取、记录为空；桌面和浏览器各测一次 200 条满载时的存档大小。

## 6. 从光标所在行试玩

**对应：** R17 / P8。总规划写明：“从当前位置开始必须明确初始状态：使用真实已记录路径或作者指定测试条件。不把临时测试变量写进来源，也不把有外部影响的动作当成无副作用跳转。”

**现状（已核实）：**

- 预览起点只有“场景开头”和各个 `@label`（`packages/editor/src/panels/preview-panel.ts:172-179`、`:560-575`）。从标签开始是直接设置执行位置，标签前的指令不执行（`packages/editor/src/preview.ts:1224` → `packages/core/src/runtime/interpreter.ts:405-423`）；变量取 `game.config.json` 的声明初值（`preview.ts:1165`）。推断：因此从标签开始时背景、立绘、BGM 都是空的。
- “回到上次位置”保存种子、入口、选择序列和目标（`packages/editor/src/preview-replay.ts:9-14`），续接时用同一入口、同一种子真实重跑，并自动做出同样的选择（`preview-replay-runtime.ts:61-131`）。
- 断点与单步已在 Core 实现（`interpreter.ts:323-391`、`:772-782`）；Editor 用“场景 + sceneHash + 指令序号”标识断点（`packages/editor/src/preview-debug.ts:13-19`）。
- 预览不能指定测试变量，只有剧情检查面板有“测试初值”（`panels/story-check-panel.ts:126-128`）。
- Authoring 的 `simulateSnapshot` 从入口穷举选择，没有目标位置参数（`packages/authoring/src/simulation.ts:168-335`）；`runExplicitPath` 按给定的标签、变量和选择一直跑到结束（`:337-387`）。仓库里没有“求出到达某一行的选择路径”的函数。

**方案：真实运行到这一行再停下，不伪造状态。**

1. 剧本工作台的每一行（正文和指令）提供“从这里试玩”，右键菜单和快捷键都能用。
2. 起点状态三选一，界面写明本次用了哪一种：
   - **按上次试玩的路径：** 最近一次试玩经过这一行时，复用“回到上次位置”的种子与选择序列，把目标从标签扩展到行。
   - **按找到的路径：** 新增 Authoring 查询“从入口出发、在预算内找一条能到达该场景该行的选择序列”，在 `simulateSnapshot` 的穷举基础上加目标和提前停止。找不到时说明原因：不可达、条件不满足、预算耗尽，与 P8 覆盖报告的分类一致。
   - **按测试条件：** 从该行之前最近的标签（或场景开头）开始，作者在表单里填变量值；只用于本次试玩，不写回 `game.config.json`。本场景之前的舞台状态此时不存在，界面会明确提示。
3. 三种方式落地为同一个机制：在目标行设临时断点，用快进真实执行到断点后暂停，作者再点“继续”。复用 Core 已有的断点、单步和快进，不新造跳转内核。因为是真的执行过，背景、立绘、BGM 和变量都与正式游玩一致。
4. 试玩中遇到的存档点、自动存档、成就和解锁仍走预览隔离，不写正式玩家数据（沿用 P7“编辑器试玩不写正式玩家 Profile”）。
5. 剧本修改后旧路径可能失效：断点与 sceneHash 绑定（`interpreter.ts:328`），失配时提示重新找路径，不停到别的句子上。

**分工：** GPT 负责 Authoring 的目标路径查询、预览续接扩展到行、测试条件起点；Claude 负责工作台入口、起点方式选择与说明、测试变量表单和失配提示。

**验收：** 三种起点各做一个真实病例：目标行跨两个场景、经过一个选择、带背景和 BGM，停下时的画面与从头正常玩到这里一致（比对背景键、立绘、BGM 语义键和变量）；不可达的行给出原因；改剧本后旧路径失配会提示；测试变量不写入来源文件。

2. **插入位置：** 场景结尾已经是 `@end` 或 `@jump` 时，新跳转插在它前面并提示；从标签节点拉线时，插在该标签段的末尾。具体规则由 GPT 按 `scene.patch insertAfter` 的语义确定。
3. **修改连线：** 拖动已有连线的终点改目标，对应 `replaceInstruction` / `replaceChoiceOption`；删除连线即删除对应指令行（需确认）。`@call` 与选择肢目前不在 `replaceInstruction` 的白名单内（`contracts.ts:239-244`），要先扩展，或明确不支持。
4. **看得见改了什么：** 每次图上编辑先显示将写入的源码差异，写入后在剧本视图高亮新行；仍走现有撤销栈与保存链，不新增第二条写盘路径。
5. **同一语义：** Editor 改为调用 Authoring 的 `scene.patch`，不再在 Editor 里拼字符串，人类和 Agent 的编辑结果一致（总规划 4.1）。

**分工：** GPT 负责确认或扩展 `scene.patch` 子操作（插入位置、`@call` 与选择肢的目标修改），并提供 Editor 可调用的入口；Claude 负责图上交互、差异预览、高亮与撤销。

**验收：** 在图上依次新建场景、连线、分支、改目标、删连线，每一步的源码差异都与手写结果一致；以 `@end` 结尾的场景连线后确实可达；撤销与重做；保存后重开；Agent 读取同一场景得到的结构与图一致。

## 8. 遮罩转场与画面滤镜

**对应：** R08 / P3 演出编排。能力矩阵 `transition-registry` 写明：“当前提供内置注册表与四种安全转场；自定义插件转场不在本轮范围。”

**现状（已核实）：**

- 四种内置转场都不截取旧画面，只作用在新的世界层上：fade 把世界层透明度从 0 推到 1；slide 让世界层从画面外滑回；circle 用 `Graphics` 画逐渐放大的圆形遮罩（`packages/renderer/src/world-effects-controller.ts:71-186`）。仓库里没有 `RenderTexture`，`extract` 只用于存档缩略图。推断：现在的转场其实是“从黑底显现新画面”，不是从旧画面过渡到新画面。
- 没有自定义着色器，唯一用到的滤镜是 `ColorMatrixFilter`（`layers/world/world-layer.ts:1237-1249`）。`pixi.js` 锁定在 8.19.0。
- 转场名在 Core Lint（`packages/core/src/scene-lint.ts:223-243`，T010）和 Renderer 类型（`world-effects-controller.ts:5`）各写一份；注册表是 WorldLayer 的私有字段，对外只有 `transition(name, ms)`。
- 时间轴 `screen` 轨道有 fade、tint、flash、wipe，没有转场动作（`packages/core/src/timeline.ts:69-77`）。
- 进行中的转场、震动、闪白、擦除都不入档，读档时直接取消（`world-layer.ts:1512-1537`）。
- 素材类别只有 background、portrait、avatar（`packages/authoring/src/contracts.ts:391`），没有遮罩图类别；Player 只把这三个目录的图片注册为纹理。
- Editor 可以编辑 `@transition`：没有列入 `INSTR_FIELDS` 的指令走通用参数编辑，`STAGE_CMDS` 也包含 transition（`packages/editor/src/panels/editor.ts:136`、`:442`）；只是没有转场名和时长的专用选择表单。
- 顺带发现：`#applyPostProcess` 以“不叠加”方式连续调用三次颜色矩阵，只有最后的对比度生效，而按 Pixi 的公式，默认值 `contrast(1)` 不是“保持不变”，而是对比度加倍（`world-layer.ts:1237-1249`；Pixi `ColorMatrixFilter.contrast`）。`setPostProcess`/`getPostProcess` 是 Renderer 公开的命令与查询（`api/renderer-commands.ts:89`、`runtime/renderer-facade.ts:753`、`:838`），仓库里没有生产调用方，但不能因此当成内部死代码。
- 顺带发现：`docs/dsl-spec.md:71` 写 `@wipe` 缺省 600 毫秒，代码实际缺省 400（`presentation-controller.ts:1376-1379`）。

**方案：**

1. **旧画面在什么时候取得。** 现在 `@bg` 会立即替换背景，之后的 `@transition` 才收到事件，那时旧画面已经没了，不能在这时截取。规则定为：每到一个停顿点（显示一句台词、出现选择、`@wait`、转场结束），之后**第一次修改舞台**（背景、立绘、图层、构图）之前，Renderer 先把当前世界层画进一张 `RenderTexture`，作为“上一停顿点的画面”；随后的 `@transition dissolve` 或 `@transition rule` 用它当旧画面，盖在已经改好的新画面上方再揭开；到下一个停顿点还没用到就释放。这样作者照现在的写法（先 `@bg`，再 `@transition`）就能得到旧→新的过渡，同一批里同时换背景和立绘也一起过渡；转场进行中发生的修改直接出现在旧画面下方；两次停顿之间没有任何舞台修改时，`dissolve`、`rule` 不产生效果。新增的只有 `dissolve`（溶解）和 `rule`（遮罩）两种，原有 fade、slide、circle 的行为不变。推断：每批修改最多多一张画面大小的纹理，开工时测量内存与耗时。
2. **遮罩转场：** 一个自定义 Pixi 滤镜，输入灰度遮罩图、进度、边缘柔和度和是否反向；灰度值低于当前进度的像素先显示新画面。写法沿用指令修饰符：`@transition rule 800 @rule=百叶窗 @soft=0.15 @reverse`。需要 GPT 确认当前走的是 WebGL 渲染（Pixi v8 若走 WebGPU 还需要 WGSL 版本），以及严格 CSP 和现有 unsafe-eval 垫片下着色器能正常编译。
3. **遮罩图是素材：** 新增 `rule` 素材类别（`content/assets/rule/`），进入素材中心、引用追踪、改名整理和打包收集（P2 素材链）。Lint 检查遮罩图是否存在，缺失时报错；运行时缺图则退回 fade 并给出诊断。
4. **转场名只登记一次：** 内置转场名放在 Core，Lint 和 Renderer 共用，消除两份列表，也为第 10 节的扩展注册留出同一个入口。
5. **时间轴放到第二步：** 本轮先做指令转场。以后在时间轴 `screen` 轨道加 dissolve、rule 时，沿用同一套规则：转场 cue 只负责盖在上面的旧画面，不拥有背景、立绘等任何属性，只在实际播放中经过起点时生效。
6. **存读档与回退只有一条规则，不分来源：** 进行中的转场不入档。读档或回退时，背景、立绘等属性按快照恢复（时间轴背景交叉淡化等现有恢复规则不变），时间轴按游标续播；任何已经开始、还没结束的转场，无论来自指令还是时间轴 cue，一律视为已完成，不再显示旧画面。因为转场 cue 不拥有属性，恢复后的时间轴也不会把它拉回半途。读档后看到的就是转场结束后的画面。
7. **画面滤镜：** 新增 `@filter` 指令，首批四种：模糊、灰度、怀旧（棕褐）、暗角；可以设过渡时长，`@filter off` 清除。只作用于世界层，不影响对白和界面；当前状态进入演出快照。灰度、怀旧这类有剧情含义的滤镜不会因低画质档而关闭，低画质只降低模糊质量。现有的 `PostProcessSettings` 属于玩家侧色彩调整，有缺陷，与作者滤镜不是一回事。它在 Renderer 公开接口上，修好还是按公开接口变更移除，由 GPT 核对公开合同和外部消费者后决定；不要在它上面搭作者滤镜。
8. **减少动态：** 新转场和滤镜过渡都遵守第 4 节的“减少动态效果”。
9. **顺手修正：** 统一 `@wipe` 缺省时长的文档与代码；Editor 补上转场专用的选择表单。

**分工：** GPT 负责 Renderer 旧画面截取、遮罩滤镜、`@filter`、Core 登记与 Lint、素材类别和存读档规则；Claude 负责 Editor 指令检查器里的转场与滤镜表单、带缩略图的遮罩图选择，以及素材中心的“转场遮罩”分类。时间轴转场与对应的 cue 编辑放在第二步。

**验收：** 真实 Player 中按现有写法先 `@bg` 再 `@transition`，在两张背景之间做 dissolve 和 rule 转场，中途截图里的旧画面确实是修改之前的画面，新画面同时可见；同一批同时换背景和立绘时一起过渡；两次停顿之间没有修改时转场不产生效果；遮罩图缺失时 Lint 报错，运行时退回 fade 并提示；转场中途存档或回退，恢复后直接显示结束画面，正在播放的时间轴续播时也不会重新出现半途的转场；滤镜状态跨存读档保持；低画质档下灰度仍然生效；减少动态下转场时长被压缩；Editor 中选择遮罩图后可以试玩；遮罩图改名后引用随之更新。

## 9. 编辑器一键导出 Windows 游戏

**执行更新（2026-10-11）：** Owner已明确授权本轮后端及本地打包验证，不再等待G4另行确认。免安装第一步已实现共享导出核心/通用Player/稳定身份与原生桥，当前验收和限制见原长期台账；接线合同见[Windows导出](../../windows-game-export-contract.md)。前端仍交Claude，安装器/签名/发行/部署未获本轮授权，也未完成，不把下方历史“未开始”现状当当前事实。

**对应：** R25、R26 / P10（未开始）。总规划 P10 已列出要求：构建配置分开显示名、稳定保存身份、版本、图标、输出目录；Windows 包真实处理 appId、安装目录、userData、设置、存档和 Profile，两部游戏并装与更新互不覆盖；沿用现有加密与包验证；在干净环境验收；本地测试打包/安装需要当轮授权（G4）。台账决策 9 要求导出在应用内闭环。

**现状（已核实）：**

- `surdet pack <目录>` 设置 `SURDET_GAME_DIR`、默认 release 模式，然后在引擎仓库的 `packages/shell` 里执行 `npm run pack`（`packages/cli/src/pack.ts:9-36`）。链路是：编译 shell → `prepare-pack.mjs` 要求项目已有构建好的 `dist/`（它不负责构建），复制 dist、`game.config.json`、更新清单和素材，并加密素材 → `verify-pack --preflight` → `electron-builder --win` → `verify-pack --artifact`（`packages/shell/package.json:14`）。

- 加密：每次打包随机生成 32 字节密钥，存于 asar 内 `game/.skey`；`content/assets` 全部转为 SDAT2（AES-256-GCM）；剧本所在的 dist 不加密，脚本注释也承认密钥可被提取（`packages/shell/prepare-pack.mjs:3-5`、`:114-141`）。
- 依赖引擎仓库：CLI 按相对路径找 shell，preflight 读仓库根 `node_modules`，还需要 electron 与 electron-builder 两个开发依赖（`pack.ts:10`、`verify-pack.mjs:168-169`、`packages/shell/package.json:33-37`）。推断：单独安装的 CLI 无法打包；首次打包要联网下载 Electron 与 NSIS。
- 游戏入口 `src/main.ts` 用 Vite 的 `import.meta.glob` 在构建时收集剧本、素材、字体、时间轴和配置（`packages/cli/templates/game/src/main.ts`），所以现在导出前必须先 `vite build`；新建项目在 Editor 里编辑、保存、试玩都不需要装依赖，但构建需要（`docs/desktop-project-creation.md:44`）。
- Editor 桌面版带有 Renderer 等运行时用于试玩、带 CLI 的建项目与 authority 代码，但**没有** shell、electron-builder、vite、npm，主进程里也没有 `child_process`（`packages/editor/scripts/build-desktop.mjs:10-51`）。
- 多游戏隔离尚未处理：游戏壳不调用 `app.setName`/`setPath`，桌面存档、Profile、设置都不按游戏区分（`packages/shell/src/main.ts:25`、`:32`、`:110`）；只有浏览器版按 `project.id` 加前缀。推断：两部游戏会共用同一个 userData，并被 NSIS 当成同一个应用，单实例锁（`main.ts:345`）也会让它们互斥。台账已把它列为发行前待办。

**结论：** 让 Editor 去调用现有 `surdet pack` 不可行：作者电脑上没有引擎仓库、npm、Vite 和 electron-builder，Editor 也不该为此起子进程、装工具链。

**推荐方案：预制运行时 + 内容清单。** 作者电脑上不跑 npm、Vite 或 electron-builder，Editor 主进程用纯 JavaScript 完成导出。

1. **通用 Player 页面（GPT）：** 在 `@surdet/player` 增加一个按清单启动的入口：读取导出时生成的内容清单（剧本、素材、字体、时间轴、鉴赏与术语配置的相对路径），在运行时加载后调用现有 `startPlayer`，代替模板 `src/main.ts` 里构建期的 `import.meta.glob`。它随 Editor 一起预先构建好。
2. **预制游戏壳（GPT）：** shell 主进程与 preload 预先构建，随 Editor 附带；运行时从包内元数据读取作品身份，按身份设置 `app.setName`、userData 路径和单实例锁，存档、Profile、设置各自隔离。稳定保存身份沿用项目 `package.json` 的 `surdet-game-<uuid>`，改作品标题不改变存档归属（P10）。
3. **Electron 运行时：** 优先复用 Editor 自身的 Electron 运行文件（同为 43.2.0），复制后改名；exe 图标和版本信息用纯 JS 的资源编辑库写入（例如 `resedit`，引入前按 AGENTS 核对许可、维护状态与体积）；asar 用 `@electron/asar` 生成。Electron 与 Chromium 的许可文件一并放入。也可以单独随附一份干净的运行时，代价是安装体积翻倍，请 GPT 评估。
4. **导出流程（Editor 主进程，Claude 做界面）：**
   1. 导出对话框：作品名、版本、图标（PNG 自动生成 ICO）、输出位置（原生目录选择）、是否加密（默认加密）。
   2. 导出前检查：全部场景编译与 Lint（有错误即阻止）、素材引用完整（缺失即阻止）、字体许可文件、已启用的扩展文件（第 10 节）。导出的是**已保存版本**；有未保存修改时先提示保存，不悄悄带上草稿（P10“默认导出已保存版本”）。

   4. 有进度、可取消；失败时清理半成品；目标目录已存在时需确认，绝不覆盖用户文件。完成后在资源管理器中显示产物。

7. **Web 包：** 同一份内容清单可以直接输出静态 Web 目录。Owner 本轮只要 Windows，所以 Editor 入口默认不做 Web 导出；现有 `surdet build --web` 保持不变。

**仍需处理的边界：**

- 改过模板 `src/main.ts` 的项目，自定义代码要改用第 10 节的扩展声明才能走一键导出；否则继续用开发者构建。

- 本地测试打包与安装需按 G4 在开工时确认授权；验收在干净目录、独立用户数据目录中进行，不碰正式游戏数据。

**分工：** GPT 负责通用 Player 入口、游戏壳身份隔离、导出核心与产物校验、CLI 改接；Claude 负责 Editor 导出对话框、导出前检查结果展示、进度与取消、完成后的说明。

## 10. 项目插件接口

**对应：** R24 / P9（未开始）。P9 已经写明边界：扩展是显式启用的受信任项目代码；要声明自己的指令和配置、UI 入口、可保存状态与释放钩子；缺扩展、版本不兼容或恢复失败时给出具体原因，不毁档；窄接口不构成隔离。

**现状（已核实）：**

- Renderer 插件只有逐帧回调：`{id, apiVersion?, onFrame, onDispose}`，回调抛错即被停用（`packages/renderer/src/plugin-host.ts:4-87`）；只能经 `RendererRuntimeOptions.pluginHost` 注入（`api/renderer-runtime.ts:86`），生产代码里没有任何注册。
- 未知指令编译成通用指令并报 W001（`packages/core/src/dsl/compiler.ts:532`、`:551-559`）；解释器发出 `'instr'` 后不等待（`interpreter.ts:1310-1316`）；唯一的生产订阅者 Renderer 对未知名称直接忽略（`runtime/presentation-controller.ts:1341-1343`）。`customInstructions` 只用来消除 W001 和相关统计。
- 战斗、日历、商店等系统指令经 `'system'` 事件路由到构造时固定的 adapter，调用 `open(payload, {pause, resume, fail})`，同一时刻只开一个（`packages/host/src/create-host.ts:15-29`、`:76-105`），没有运行期注册。
- 转场注册表是 WorldLayer 的私有字段，没有外部注册入口（`packages/renderer/src/world-effects-controller.ts:193`、`:210-214`）；也没有文字效果的注册入口。
- 预览 iframe 与 Editor 同源且没有 `sandbox` 属性（`packages/editor/src/panels/preview-panel.ts:604-605`），Editor 页面没有 CSP；父窗口收消息只比对来源窗口，`load`、`trace`、`ready` 消息的目标 origin 是 `'*'`（`preview-panel.ts:96-101`、`:1093`）。推断：项目代码一旦在预览里执行，就和 Editor 页面处在同一个信任边界内。

**方案：**

1. **声明：** 项目在配置中列出扩展：入口文件、apiVersion、声明的指令名与参数、要保存的状态版本。普通内容不能自动注册代码；未启用的扩展不加载。
2. **一个入口，按 P9 范围注册：**
   - **指令：** 名称、参数校验、是否阻塞、执行函数（返回完成或失败），以及可选的保存/恢复。声明过参数的指令由 Lint 校验参数，取代 `customInstructions` 只消警告的做法。
   - **系统界面：** 沿用 `system-router` 的 `open(payload, {pause, resume, fail})` 合同，允许扩展在启动时注册 adapter，不另造一套暂停与恢复。
   - **转场与滤镜：** 把转场注册表从 WorldLayer 私有字段提升为 Renderer 的公开注册入口；第 8 节的遮罩转场作为第一个内置实现，走同一个入口。
   - **逐帧回调：** 保留现有 `plugin-host`。
   - 文字效果暂不开放，等第 3 节第三批之后看真实需求。
3. **保存：** 扩展状态带版本写进存档；读档时缺扩展、版本不兼容或恢复失败，在改动当前运行状态之前明确拒绝并说明原因，不让玩家继续覆盖好档。
4. **未授权或缺失的扩展：停下，而不是跳过。** 没有确认信任的项目照常可以打开和编辑。试玩运行到需要扩展的指令或系统时，明确停下并说明“这一步需要启用扩展”，不跳过继续：扩展可能修改变量或阻塞推进，跳过会造出错误的剧情状态。停下的这次试玩不产生可用的续接路径、存档或审阅依据；剧情检查和覆盖报告把这类分支记为“需要扩展，未运行”。作者在 Editor 中确认信任（列出代码来源、入口文件和运行环境的真实能力）之后，预览才执行扩展代码。以后如果确实需要“占位继续”，必须作为单独命名的模式，不能冒充正常试玩。
5. **隔离边界如实写明，本轮不调整：** 预览 iframe 与 Editor 同源、没有 sandbox，父窗口只比对来源窗口，部分消息的目标 origin 是 `'*'`。启用后的扩展代码与 Editor 页面在同一信任边界内。本轮不改 iframe、CSP 或权限，列为待评估；将来即使加上 sandbox，也不能据此宣称已经隔离（总规划 4.4）。
6. **构建：** 导出（第 9 节）时把已启用的扩展一并打包，缺文件则在导出前报错。
7. **AI 可见：** Agent 通过能力发现读取扩展声明、参数和校验结果；普通内容 Agent 不能借注册扩展取得额外权限（P9）。

**分工：** GPT 负责 Core、Host、Renderer 的注册入口、试玩停下的语义、存档合同、Lint 与构建；Claude 负责 Editor 的信任确认、扩展列表与诊断显示，以及试玩停下时的说明界面。

**验收：** 按 P9 原定：用一个剧情交互面板和一个可保存的小互动证明接口够用；禁用、损坏、版本不兼容的扩展都失败得清楚且不毁档；未确认信任的项目试玩到扩展指令时停下，不生成存档、续接路径或审阅依据；反复打开关闭能释放资源；没有扩展的普通项目不增加任何配置。P9 表中八项既有玩法接线是总规划自己的验收项，本文不重复也不替代。
